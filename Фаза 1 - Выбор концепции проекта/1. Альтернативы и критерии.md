## A1. MusicApp

**Проблема.** Нужен единый доступ к небольшому музыкальному каталогу и удобная личная библиотека: найти и послушать трек, сохранить его, собрать плейлист и следить за исполнителями.

**Пользователи.** Слушатель и администратор каталога. Посетитель — слушатель до регистрации. Владелец плейлиста — слушатель, создавший плейлист. Это состояния основных ролей, а не дополнительные роли.

**Исполнитель** — сущность каталога: карточка с треками. Отдельного кабинета исполнителя и самостоятельной загрузки музыки артистами в MVP нет. «Подписка на исполнителя» — отслеживание его страницы, а не платёж.

**Граница системы.** Веб-приложение целиком: веб-интерфейс, монолитный backend, база данных метаданных и объектное хранилище аудиофайлов. Каталог один, тестовые записи предоставляет команда.

### Предварительные пользовательские цели

| ID | Пользовательская цель | Основная роль |
|---|---|---|
| UC-01 | Зарегистрировать учётную запись | Посетитель |
| UC-02 | Войти в систему и завершить сеанс | Слушатель |
| UC-03 | Найти треки и исполнителей по запросу | Слушатель |
| UC-04 | Открыть страницу исполнителя и его каталог | Слушатель |
| UC-05 | Прослушать выбранный трек и управлять очередью воспроизведения | Слушатель |
| UC-06 | Сохранить музыку в избранное и управлять этим списком | Слушатель |
| UC-07 | Создать плейлист | Слушатель |
| UC-08 | Изменить плейлист, состав и порядок треков либо удалить его | Владелец плейлиста |
| UC-09 | Опубликовать плейлист по ссылке и открыть доступный по ссылке плейлист | Владелец и слушатель |
| UC-10 | Подписаться на исполнителя и управлять своими подписками | Слушатель |
| UC-11 | Просмотреть историю прослушивания и повторно запустить трек | Слушатель |
| UC-12 | Запустить персональную музыкальную подборку | Слушатель |
| UC-13 | Загрузить аудиофайл и опубликовать трек с метаданными | Администратор |
| UC-14 | Обновить каталог: карточки исполнителей и данные треков, убрать недоступную запись | Администратор |

Обозначения UC-01…UC-14 сохраняются для фазы 3. Это предварительный уровень целей. Он не равен числу HTTP-методов и не является готовой оценкой UCP. Если в фазе 3 какой-то сценарий окажется слишком широким (например, UC-05 или UC-14), группировку пересмотрим так, чтобы осталось 10–15 содержательных сценариев.

### Границы MVP

- Только веб-приложение и один каталог; аудио хранится отдельно от метаданных.
- Потоковое воспроизведение, поиск по названию и исполнителю, избранное, плейлисты, подписки на исполнителей.
- Плейлисты приватные; опубликованный плейлист можно открыть по ссылке. Совместного редактирования нет.
- Простая персональная подборка: на основе избранного, подписок и популярности, с запасным вариантом для нового пользователя. Без обучения собственной ML-модели, без нейросетевых эмбеддингов и обещаний качества рекомендаций.
- У трека один основной исполнитель и необязательные приглашённые (feat). Отдельной системы альбомов нет.

**Исключено из MVP:** платные тарифы и биллинг, реклама, офлайн-режим, мобильные приложения, подкасты, социальные ленты, чат, кабинет исполнителя, интеграции со Spotify и Яндекс Музыкой, массовый импорт коммерческих каталогов.

**Технический контекст.** Монолитный backend (Java/Spring Boot), веб-интерфейс (React), реляционная БД (PostgreSQL) и объектное хранилище (MinIO) для аудио. Микросервисы, Kubernetes, Kafka и ML-платформа не нужны.

**Пригодность для COSMIC и UCP.** Функциональные пользователи — слушатель и администратор; граница измерения — веб-система целиком, поэтому UI, backend, БД и хранилище находятся внутри. Движения данных хорошо различимы: запрос поиска и выдача результатов (Entry/Exit), чтение каталога (Read), запись избранного, плейлистов, подписок и истории (Write). Для UCP есть два человеческих актора, 14 целей средней сложности и естественные альтернативные потоки: пустой поиск, удалённый трек, чужой плейлист, ошибка файла.

**Допущение для учебного планирования.** Рассматривается разработка согласованного MVP с нуля. Имеющиеся у команды заготовки репозиториев MusicApp и прошлые часы разработки в оценки и в историю работы по предмету не включаются.

## A2. Jarvis с локальной базой документов

**Проблема.** Человеку с большим набором собственных документов (конспекты, статьи, инструкции) трудно быстро найти ответ и проверить, откуда он взят. Облачные помощники не всегда допустимы по соображениям приватности.

**Пользователи.** Один пользователь локальной установки. Предлагаемая версия для сравнения; это не описание текущего проекта пользователя.

**Граница системы.** Локальное приложение: интерфейс, база документов, поисковый индекс по фрагментам, история диалогов. Языковая модель — готовый внешний компонент на том же компьютере; её не обучают и не дообучают.

### Пользовательские цели

| № | Цель |
|---|---|
| J-01 | Добавить документы в локальную базу (PDF, DOCX, TXT, Markdown) |
| J-02 | Организовать документы в коллекции, просмотреть и удалить документ |
| J-03 | Задать вопрос по базе и получить ответ с фрагментами-источниками |
| J-04 | Ограничить вопрос выбранной коллекцией или документами |
| J-05 | Открыть источник ответа на месте цитируемого фрагмента |
| J-06 | Продолжить диалог уточняющими вопросами с учётом контекста |
| J-07 | Просмотреть, переименовать и удалить диалоги |
| J-08 | Получить краткое содержание документа |
| J-09 | Получить сводку по нескольким выбранным документам |
| J-10 | Найти фрагменты по ключевым словам без генерации ответа |
| J-11 | Отметить ответ как полезный или неверный |
| J-12 | Экспортировать диалог или конспект в Markdown |
| J-13 | Настроить помощника: модель из установленных, длина и язык ответа |

**Исключено из MVP:** обучение и дообучение модели, голосовое управление, управление компьютером и файлами вне базы, распознавание сканов (OCR), многопользовательский режим, облачная синхронизация, интеграции с почтой и мессенджерами. Установка Docker, служебные проверки состояния и обработка внутренних ошибок пользовательскими целями не считаются.

**Пригодность для COSMIC и UCP.** Человеческий актор один; языковая модель — внешний функциональный пользователь-система, если граница измерения проходит вокруг приложения. Движения данных различимы (запрос, чтение фрагментов, обмен с моделью, запись истории). Риск для оценки: значительная часть сложности — качество ответов и подбор фрагментов, а функциональный размер этого не отражает.

## A3. Заявки на ремонт в общежитии

**Проблема.** Заявки на ремонт подают устно или в общих чатах, они теряются; студент не видит статус, диспетчер не видит загрузку мастеров и просрочки.

**Пользователи.** Студент, диспетчер, мастер, администратор.

**Граница системы.** Веб-приложение одного общежития: заявки, фото, статусы, назначения, отчёты.

### Пользовательские цели

| № | Цель | Роль |

| R-02 | Отслеживать статус своих заявок и уведомления в системе | Студент |
| R-03 | Дополнить или отменить заявку до назначения мастера | Студент |
| R-04 | Классифицировать заявку и задать приоритет | Диспетчер |
| R-05 | Назначить или переназначить мастера | Диспетчер |
| R-06 | Согласовать время визита | Мастер, студент |
| R-07 | Принять заявку в работу и отмечать ход выполнения | Мастер |
| R-08 | Закрыть работу с комментарием и фото результата | Мастер |
| R-09 | Подтвердить результат или повторно открыть заявку | Студент |
| R-10 | Просматривать очередь и просроченные заявки | Диспетчер |
| R-11 | Оценить качество выполненной работы | Студент |
| R-12 | Сформировать отчёт по заявкам за период | Администратор |
| R-13 | Вести справочники: комнаты, категории работ, мастера, учётные записи | Администратор |

**Исключено из MVP:** закупки материалов и склад, бухгалтерия и оплата, несколько общежитий, мобильное приложение, SMS и мессенджеры, интеграция с системами университета.

**Пригодность для COSMIC и UCP.** Четыре актора и выраженный жизненный цикл заявки дают много различимых движений данных и альтернативных потоков: отмена, отказ, повторное открытие, просрочка. Работы и зависимости для фазы 5 выделяются естественно.

## A4. Бронирование оборудования студенческого клуба

**Проблема.** Оборудование клуба (камеры, микрофоны, проекторы) выдают по договорённости в чате. Неизвестно, что свободно, кто держит вещь и в каком она состоянии; возвраты затягиваются.

**Пользователи.** Участник клуба и ответственный за оборудование.

**Граница системы.** Веб-приложение одного клуба: каталог, календарь доступности, заявки, выдача и возврат, обслуживание, отчёты.

### Пользовательские цели

| № | Цель | Роль |
|---|---|---|
| B-01 | Просмотреть каталог и проверить доступность на нужные даты | Участник |
| B-02 | Подать заявку на бронирование | Участник |
| B-03 | Изменить или отменить свою заявку | Участник |
| B-04 | Одобрить или отклонить заявку | Ответственный |
| B-05 | Выдать оборудование по заявке | Ответственный |
| B-06 | Принять возврат и зафиксировать состояние | Ответственный |
| B-07 | Запросить продление и получить решение | Участник, ответственный |
| B-08 | Сообщить о повреждении или неисправности | Участник |
| B-09 | Отправить оборудование на обслуживание и вернуть в фонд | Ответственный |
| B-10 | Контролировать просроченные возвраты и напоминать участнику | Ответственный |
| B-11 | Вести каталог оборудования | Ответственный |
| B-12 | Просмотреть историю своих бронирований | Участник |
| B-13 | Сформировать отчёт об использовании оборудования | Ответственный |

**Исключено из MVP:** оплата и залоги, доставка, закупки, несколько клубов, интеграция с внешними календарями, мобильное приложение.

**Пригодность для COSMIC и UCP.** Два актора, понятные состояния брони и экземпляра оборудования, хорошо различимые записи и чтения. Конфликты дат, просрочки и повреждения дают альтернативные сценарии.

## Критерии

| Код | Критерий | Тип | Что оценивается |
|---|---|---|---|
| K1 | Полезность продукта для выбранных пользователей | максимум | Насколько продукт решает реальную и регулярную проблему своих пользователей |
| K2 | Понятность предметной области членам команды | максимум | Насколько участники уже понимают роли, процессы, правила и термины области |
| K3 | Пригодность для фаз 3–5 | максимум | Даёт ли концепция 10–15 различимых целей, ясные движения данных, альтернативные сценарии, работы и зависимости |
| K4 | Трудоёмкость учебной проработки | минимум | Сколько усилий команды потребуют фазы 2–5 по этой концепции: Use Cases, COSMIC, UCP, декомпозиция, план |
| K5 | Интерес участников команды к теме | максимум | Насколько участникам хочется работать над темой весь семестр |

**K4 — это трудоёмкость учебной работы, а не разработки продукта.** Продукт по фазе 5 воображаемый и в рамках предмета не разрабатывается. K4 измеряет, сколько времени команда потратит на описание, оценивание и планирование этой концепции.

**Отличие K2 от K4.** K2 описывает исходное знание команды, K4 — объём предстоящей учебной работы. Знакомая область может требовать много работы (много ролей и сценариев), а незнакомая — оказаться компактной. Поэтому высокая K2 не означает автоматически низкую K4.

**Проверка на дублирование.**

| Пара | Почему это разные критерии |
|---|---|
| K1 — K5 | K1 — ценность для внешних пользователей продукта, K5 — личная мотивация команды |
| K2 — K3 | K2 — что команда знает, K3 — насколько структура концепции подходит под методы следующих фаз |
| K3 — K4 | K3 — качество материала для методов (выгода), K4 — объём работы (затраты); концепция может быть удобной, но объёмной |
| K2 — K4 | Знание области и объём работы различаются (см. выше) |
| K1 — K3 | Полезный продукт может иметь размытые сценарии, и наоборот |

Ожидаемые веса критериев здесь не приводятся: веса определяются только по ответам экспертов.

## Шкалы

### TOPSIS: оценки 1–9

Оценки целые от 1 до 9; 2, 4, 6, 8 — промежуточные. Важность критерия: 1 — практически не важен, 3 — слабо, 5 — умеренно, 7 — сильно, 9 — решающий критерий.

| Балл | K1 Полезность | K2 Понятность области | K3 Пригодность для фаз 3–5 | K4 Трудоёмкость (меньше — лучше) | K5 Интерес |
|---|---|---|---|---|---|
| 1 | проблема надуманна, продукт почти не нужен | никто не знаком с областью, нужны внешние консультации | цели сливаются или их меньше 10, данные и работы неясны | минимальная: всё готовится без дополнительного изучения | совсем неинтересно |
| 3 | польза эпизодическая, проблему легко решить иначе | общие представления, многое придётся выяснять | часть целей различима, акторы, данные или зависимости размыты | небольшая: отдельные уточнения | скорее неинтересно |
| 5 | заметная польза, но есть приемлемые альтернативы | основные роли и процессы понятны, отдельные правила надо уточнять | 10–15 целей, но границы части сценариев надо пересматривать | средняя: заметный объём описаний и уточнений | нейтрально |
| 7 | заметно упрощает регулярную задачу | область хорошо понятна большинству | цели различимы, данные и работы понятны, есть мелкие неясности | высокая: много сложных сценариев или незнакомых механизмов | интересно |
| 9 | решает острую регулярную проблему | все уверенно знают роли, процессы и термины | 10–15 чётких целей, ясные акторы, данные, альтернативные сценарии и зависимости | очень высокая: заметно больше, чем у остальных | очень хочу работать над этой темой |

Для K4 эксперт оценивает саму трудоёмкость (9 — очень трудоёмко). Направление «меньше — лучше» учитывается при нормировании, а не при заполнении.

### МАИ: шкала Саати

Сравниваются только независимые пары «левый — правый». Ответ показывает, какой объект предпочтительнее и во сколько раз: 1 — равная предпочтительность, 3 — умеренное, 5 — существенное, 7 — значительное, 9 — абсолютное превосходство; 2, 4, 6, 8 — промежуточные. Обратные элементы матрицы вычисляются как 1/a_ij.

- Критерии сравниваются по важности для выбора концепции.
- Альтернативы по K1, K2, K3, K5 сравниваются по тому, какая лучше по критерию.
- **По K4 предпочтительнее альтернатива, которая требует меньше учебной трудоёмкости.** Если A1 проработать легче, чем A2, ответ — «левый ×N».
